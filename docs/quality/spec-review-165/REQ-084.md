## REQ-084 — 完整用户目录及用户上下文操作

> "完整用户管理：按全局用户去重提供分页、筛选、搜索、详情和企业成员关系，含注册与登录、状态、费用、VIP、任务及内容入口；联系资料按字段授权展示，不把多企业成员算作多个用户。"
> — `docs/requirements/01-srs.md:L206`，REQ-084，P0。

**Verdict:** partial · confidence: high（静态源码结论，未运行 UI、API 或测试）

**What this demands of an implementation:** 管理员从按全局 `user_id` 去重的目录搜索、筛选并翻页后，可进入唯一用户详情，查看当前授权范围内的成员关系、注册/登录和状态，并直接以该用户为目标进入费用、VIP、任务与内容流程。联系方式的显示和搜索均受字段权限限制，不能借搜索推断未获准的联系方式。相关后台细则进一步明确：详情是主要操作入口，不要求管理员手工拼接用户 ID（`docs/product/08-admin-dashboard.md:L83`）；组合筛选需由 URL 保留（同文档 `L89`）。

**F084-01 · P1 · 费用/VIP 操作丢失当前用户目标。** 用户详情加载的是上述响应包装对象（Admin `src/main.tsx:L2215`），但传给 `BillingModal.user` 的是 `...data`，不是 `data.user`（`L2390-L2399`）；包装对象没有顶层 `id`，因此两个实际消费点得到 `undefined`（`L1847`、`L1857`）。`user?: any` 使类型检查不能阻止此错配（`L1835-L1840`）。

VIP 的影响比“未预填”更明确：父层仍创建了 truthy 的 `subject` 对象；`VipCommandModal` 将类型选择与目标 ID 均锁定，ID 的初始值却为 `undefined`，输入又为 `required`（Admin `src/vip.tsx:L960-L978`）。源码确定其成为空的只读必填目标，管理员无法补填当前用户 ID；若绕过表单约束，预览从 `FormData` 读取目标并请求 `/subjects/${kind}/${selected.id}`，仍没有从用户详情恢复目标的逻辑（`L660-L688`）。这是静态可复现调用链，未声称观察到浏览器运行结果。

费用则因为 `subject` 为假而省略 `subject_id`，请求 `/v1/admin/billing/accounts?limit=50`（Admin `src/fees.tsx:L486-L519`）。服务端仍执行 `admin.billing.read` 和账户范围限制，但只有存在 `q.subject_id` 才追加目标主体条件（Platform `src/admin-billing.ts:L65-L88`）。因此列表会退化为管理员当前可见范围内的账户列表，失去“正在管理哪个用户”的约束；不是已证实的越权读写，也不声称一定会给错误用户入账。用户详情已返回的 `billing_account_ids` 当前没有被 Admin 前端消费，不能补救本调用路径。

静态复现条件：具备相应读写权限和有效 Admin 会话 → `/users` 点任意一名用户 → 详情点“开通 VIP”或“调整费用” → 按上述对象结构跟踪目标 ID。权限不足本身不是该缺陷的触发条件。

**F084-02 · P2 · 用户详情没有该用户的任务/内容入口。** 完整读取 `UserDetail` 的返回树后，仅有返回列表链接、账号/成员管理、费用/VIP 操作、成员统计和个人权益；任务只是数值统计，没有任务或内容链接/面板（Admin `src/main.tsx:L2207-L2419`，任务计数 `L2336-L2341`）。这与 REQ-084 的明确“任务及内容入口”以及后台规格的用户详情入口要求不一致。

一般侧栏的 `/execution`、`/content` 页面确实存在，但它们不会接收选中用户：通用 `Section` 请求只传页码、每页大小和自由搜索（Admin `src/main.tsx:L1092-L1099`）；通用后端分页参数只有 `page/page_size/search/tenant_id`（Platform `src/admin.ts:L47-L52`），没有用户条件。任务集合有 `created_by`（`L142`），但内容集合投影不输出统一所有者字段（`src/admin-content.ts:L83-L88`）。因此不能把“手工打开通用页面”或“把用户 ID 填进搜索”算作已经接通该用户的任务/内容入口。判断不要求补做所有内容授权组合测试。

**F084-03 · P2 · 用户目录筛选不保留在 URL。** 应用筛选仅更新组件内 `filters` 和游标状态（Admin `src/main.tsx:L1357-L1366`），搜索也只更新组件状态（`L1328-L1333`）。路由改变时清空 `filters`，只从 URL 恢复 `search/view`（`L1057-L1071`）；详情的返回链接固定为 `/users`（`L2223`）。因此打开详情再返回或刷新目录会丢失原筛选，无法分享/恢复该筛选视图，直接违反后台规格 `L89` 的“URL 保留条件”。这不是后端筛选失效，后端对收到的受支持参数有真实约束。

**How the verdict was reached:** 判为 `partial`，因为用户主表去重、受限目录搜索/筛选、服务端游标、详情身份字段、成员关系和联系方式字段鉴权均存在具体执行路径；不是 `absent`。又因为详情发起的 VIP/费用路径存在确定的对象形状错配，任务/内容上下文出口缺失、筛选 URL 恢复缺失，不能判为 `implemented`。这也不是整体 `contradicted`：其主体设计确实遵循全局用户唯一与字段权限要求，缺陷集中于具体用户的后续操作及状态衔接。

上述三项是原始源码的候选缺口，待父任务独立反驳；本检查没有把既有测试通过、函数名、一般侧栏、历史完成标记或假外部接口，替代为当前功能闭环的证明。

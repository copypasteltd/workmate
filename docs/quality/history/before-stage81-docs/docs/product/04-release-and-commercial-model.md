# 发布路线与商业模型

版本：1.5 · 2026-10-18。阶段顺序为设计默认，可依据客户硬需求调整；没有预算和人员基线时不承诺固定日期。

## 1. 完整发布范围

| 阶段 | 可交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0 能力验证 | Codex 固定版本与内部网关的工具循环/事件/恢复验证、真实图像、模板视频、数据计算及原生执行可行性 | Codex 集成及关键依赖有实际结果，能力注册表无隐含支持声明 |
| M1 Web 工作台及导入试点 | 原有会话、角色、Skill、云文件、成果及素材/报告业务；Admin 用户与用量、人工费用/VIP、内容/任务控制、独立身份、权限审计与安全配置基础 | 真实用户工作和 G10 后台基础通过；可主动开通且金额、权限、权益生效和审计可核对 |
| M2 协作及连接器 Web MVP | 共享项目、专业团队、方案、基础云端计划及首个正式广告连接器；后台完整批量/导出、公开目录与公告/菜单/功能发布 | 本阶段验收及 G10 扩展通过；协作、连接器、批量部分结果和配置回滚有实际证据 |
| M3 浏览器与本地 | 扩展侧栏/网页上下文、Native Messaging host、目录授权、跨端接续 | 设备离线、撤销、路径边界、重复执行和资源清理通过 |
| M4 完整产品 | Desktop、更多平台连接、生成式视频/效果/语音、SEO/GEO、更多企业 SOP 与事件流程 | 各能力真实验证、独立质量样例与可持续支持成本 |
| M4 后增量 | 独占云电脑、实时画面、自动发布/预算优化、更多企业系统与操作系统 | 单独业务范围、授权、成本、运行验收通过 |

M4 可分多个增量版本，不将所有能力绑定在同一天上线。M3 本地能力如为试点刚需，可提前与 M1 并行准备；这不会取消 Web 的完整云端使用路径。

本轮以 [WorkBuddy / Accio 对标](../research/01-web-benchmark-workbuddy-accio.md) 修订 Web 基线。REQ-032/033 的通用模板与时间触发提前到 M2；特定企业系统事件仍随相应连接器阶段开放。基础云文件属于 M1，多专业团队属于 M2，不依赖 REQ-059 的专属电脑采购。

## 2. 客户接入与服务包

建议首次接入服务包括：梳理三项真实工作、整理品牌资料、配置账户授权、制作验收样例、培训与试点复盘。新增复杂连接器、专业工程导出及定制 SOP 分别估价。

订阅组合建议为企业基础服务/席位 + 包含用量 + 明确的媒体与高资源用量。所有价格均待内部成本和客户意愿验证，文档不虚构港币单价。

## 3. 单位经济模型

收入 = 订阅 + 用量 + 接入/定制服务。直接成本包括全部成功和失败模型调用、媒体、执行算力、存储流量、第三方工具、人工修订与支持。每次成功交付成本分母仅计客户接受的交付，不能排除失败成本。

高推理强度、视频和大量变体分别观察，不只看平均 token 价。免费试用也设明确额度；增加预算与采购是企业行为，不因模型建议自动发生。

## 4. 推广与退出条件

先在现有客户团队试点，记录实际交付证据，再决定扩大同类客户。客户可导出项目和交付资产，停用连接与设备，按数据生命周期离场。

某能力连续出现低接受率、成本不可控或缺少正式平台权限时，可暂停该能力的新任务并修复；保留已有产物和真实状态，不把能力暂停解释为完整产品交付结束。

## 5. 需求及工程变更

需求冻结以 REQ 编号、能力版本、测试集和交付文件为单位。新增渠道/效果/连接器须同步输入输出、价格单位、异常、权限、支持范围和验收样例。对已有客户的权益变化记录生效时间，不静默改变运行中任务。

## 6. 预设角色的发布条件

ROLE01 新增首个角色版的硬门槛：至少 12 个不同、通过运行验收且可直接选用的角色，同时覆盖软件开发与设计，含 Codex＋设计 Skill＋Image 2 的设计师。本次 [18 个角色](06-role-templates-and-skill-presets.md) 是设计目录；未验证、禁用、改名副本、仅咨询和仅提示词条目不计入数量。

M0 增加 Codex 固定版本加载技能、内部 Image 2 真实生成/编辑及字体分层验证。M1 完成角色目录、自动绑定、版本定制和至少 12 个合格角色；建议优先 R01–R16 的开发与设计角色。R17 可先使用导入数据，R18 的可执行流程和自动计划随 M2 开放；生成式视频和配音仍逐能力验收，不是基础视频角色成立的前提。

每个计数角色保存完整任务、产物修改、依赖/越权异常三类运行证据和版本、费用、业务评价。角色选择页上线前核对计数及专业覆盖，不能把静态契约校验当作资格通过。具体工作包为 RP01–RP06，见角色分册；订阅权益和媒体限额仍由企业方案管理。

## 7. 品牌设计发布条件

BRAND01 将官网品牌一致性纳入首个对客版本，拆为 REQ-081/082 与 G09。M1 的登录、新工作、角色、会话/成果及代表素材/报告页面采用 [官网同源规范](07-brand-design-system.md)，完成浅深主题、繁中英文、控件状态、窄屏、键盘/对比与缩放验收。管理页面沿用同一组件，不另设后台配色。

M3 扩展和 M4 Desktop 分别追加端内代表视图与原生窗口/面板检查。客户作品主题独立，平台主题切换不影响编辑工程或导出文件。当前取样、token 和静态样板是设计证据；实际产品视觉发布资格仍需运行截图与检查记录。

## 8. Admin 与人工商业开通门槛

ADMIN01 / G10 要求运营后台随 M1 试点提供，开发拆为 [AD01–AD10](../technical/11-admin-control-plane.md)。M1 验证完整用户目录、消耗追溯、权限范围、人工费用、VIP 生效/到期、内容管理与审计；M2 补完批量、导出、用户端公开内容发布和更广配置。正式自动收款、发票及订阅扣款仍按独立商业接入验收，不成为人工开通的前置依赖。

充值必须有真实确认收款，赠送另记促销额度；VIP 默认不自动续费，不视作无限余额或资源权限。各项操作记录主体、来源、金额或时段、版本、原因和操作者；并发重复、超额退款、过期授权或审计失败不得产生错误权益与资金记录。角色权限和数据范围在 API、worker、下载及三端新调用均复核，不能仅验证后台按钮可点击。

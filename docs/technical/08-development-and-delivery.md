# 开发实施与交付指南

版本：1.5 · 2026-10-18。本仓库当前交付文档及契约；以下工程目录和应用命令为后续实施约定，不表示源代码已存在。

实际开发与构建根目录固定为 `D:\dev\copypasted\自有agent\`，以下工程路径均相对于该根目录；全部文档、文档工具和核查报告在其 docs 子目录维护。命令必须直接使用 D 盘工作区，具体见 [路径规范](../governance/03-workspace-and-path-policy.md)。

上述六个仓库现已建立，各端具有锁文件、独立快照、中英 README 和真实截图。0.1.0 实际实现、与长期契约的差异及启动方式见 [实施清单](12-implementation-and-repositories.md)；下方工作包保留完整规划，不能据此声称全部完成。文档工具继续位于 docs/tools。

## 2. 原生本地环境

使用原生 Git、Node.js 受支持 LTS、包管理器、PostgreSQL 和 FFmpeg；Chromium 作为受控渲染依赖。本地对象存储先用文件系统适配，不为开发要求安装对象存储容器。

不执行 Docker、WSL、虚拟机或依赖它们的脚本。Windows 安装官方原生组件或使用已授权的远端开发服务；macOS/Linux 同样用原生安装路径。精确版本在 M0 兼容表记录并锁定。

可先用 `node --version`、`git --version`、`psql --version`、`ffmpeg -version` 核对已安装依赖；这不等于启动服务。配置使用 task-specific 变量，不覆盖 HOME 或 CODEX_HOME。

## 3. 配置与凭证契约

配置类包括数据库、对象适配、产品 public URL、会话/签名密钥引用、内部 AI base URL/能力映射、平台 OAuth、设备控制面、资源限额和保留策略。生产密钥由部署密钥设施注入，示例文件只含明显占位值。

缺少内部 AI 凭证时可开发 contract mock，但必须标记模拟数据。真实能力验收使用内部网关正式受限凭证，不在聊天或文档中粘贴真实 Key。所有能力开关默认按已验证状态开放。

## 5. 测试与 CI 目标

原生 CI 阶段：格式/类型 → 合同与 schema → 数据库迁移 → 指标及状态单元测试 → API/worker 集成 → 三端 E2E → 媒体质量样例 → 发布包验证。测试使用虚构固定数据；真实内部 AI smoke 单独受控运行，费用上限明确。

未来脚本约定为 contracts:check、typecheck、test:unit、test:integration、test:e2e、build 和 package；这些应用脚本需初始化后实现，当前不声称可直接运行。

当前可运行的文档核查命令是 `python -X utf8 docs/tools/validate_docs.py`，依赖原生 Python、jsonschema/referencing 和 cryptography，版本见 [依赖清单](../tools/requirements.txt)，不启动浏览器或虚拟化环境。

## 6. 代码评审与定义完成

每次需求实现关联 REQ、operationId 和 TC；检查授权、幂等、错误、计量、资源清理与迁移。可逆低影响编辑不机械增加镜像实现的测试；状态、计算、费用和外部副作用必须有有意义测试。

完成一个工作包需要实现、契约、迁移/配置、测试结果、运行证据和维护说明。文档完整不替代真实网关、平台、媒体或客户端测试。正式发布还需备份恢复、回滚和试点负责人接受。

## 7. 角色预设工作包增补

在既有 19 个工程包之上增加 RP01–RP06：目录标准、专业技能包、Codex/内部 Image 2、选择与自动绑定、企业定制/版本、角色资格验收。它们是既有 Agent/技能、网关、媒体和质量模块的子工作包，避免另建相互独立的运行系统。具体产出及 REQ 映射见 [角色分册](../product/06-role-templates-and-skill-presets.md)。

依赖顺序：定义角色交付与验收 → 封装/验证技能和内部能力 → 版本解析及实例化 → 前端目录与成果迭代 → 逐角色真实验收及计数。至少十二个不同合格角色、开发/设计覆盖及指定设计师为首版发布门槛。文档目录/schema 由 build_role_presets.py 生成，已接入 build_contracts.py；此脚本不安装技能、不运行内核、不调用图像模型。

## 8. 品牌设计实施与检查

REQ-081/082 由 DEV-10 建立共用基础，DEV-11/13 和所有管理页面复用。先固化官网来源和 token → 实现主题/字体/Logo 与基础组件及状态 → 形成首页、角色、会话/成果、素材/报告代表页面 → 执行跨端、键盘/对比/缩放和客户作品隔离检查。具体要求见 [前端设计集成](10-frontend-design-system.md)。

品牌工具 [build_brand_design.py](../tools/build_brand_design.py) 只生成 docs 内设计 token、CSS 和离线样板；[verify_brand_preview.py](../tools/verify_brand_preview.py) 使用原生独立无头浏览器检查样板并在 finally 关闭页面/上下文/浏览器。它与不启动浏览器的 validate_docs.py 分开运行，样板结果不计为完整产品 G09 通过。本轮内核方向调整复用既有视觉证据，未重新生成或运行样板。

## 9. Admin 开发主线与交付

ADMIN01 在 DEV-03/04/05/10/17 及 M11 费用基础上拆为 [AD01–AD10](11-admin-control-plane.md)：身份、用户、用量、资金、权益、内容、目录、权限审计、前端和联调。AD01 与 AD08 的独立身份、服务端权限和事务审计先于任何后台写入；随后构建读模型、账本/权益事务及内容控制，最后完成品牌页面、批量发布和跨端联调。八类角色种子来自明确权限清单，生产初始超管通过受控一次性流程建立，不能提供默认密码。

M1 必须具备完整用户详情、用量钻取、人工充值/赠送/退款、VIP 开通/到期/撤销、核心内容/任务控制与审计；M2 完成批量、导出、公开配置与目录管理。具体页路由、字段和状态见 [产品设计](../product/08-admin-dashboard.md)。自动支付接入可后续实现，人工费用和权益不能整体推迟到 M4。

契约源为 [build_admin_contracts.py](../tools/build_admin_contracts.py)，由 build_contracts.py 调用并输出 OpenAPI、权限目录及虚构样例，再由 build_quality.py 生成 102 项追踪和用例。静态校验不启动产品或支付服务；交付 AD 包还需数据库迁移、权限拒绝、并发与故障测试、实际页面、跨端生效和业务验收证据。全部 TC-083–102 当前为 not_run；G10 未通过前不能把文档示例计作实际开通。
